## 实测问题与根因修复

- 64 用户原始日志显示，共享 Redis 客户端达到默认 100 连接上限后立即抛出 `Too many connections`。会话续租因此取消执行任务；`SERVER_RESTART` 同时表示执行租约失效，日志中没有实际 API 重启证据。原始版本的 64 用户档也出现同类错误。
- `RedisCache` 使用标准异步 `BlockingConnectionPool`，保留 100 连接上限，短时耗尽时最多等待 5 秒；超时仍向直接调用者抛错。缓存旁路、会话租约、模型配额与 fencing 规则保持原语义。真实 Redis 测试占满 100 连接，覆盖释放后继续执行及等待超时：[41 项回归](../../../eval/verification/2026-10-14-r1-pool-fix/pytest.log)。
- 读取运行／重连接口会校验会话归属，原 `assert_owner` 对已有会话也申请写锁。已绑定归属改为普通读连接核对；创建和可信绑定仍在原事务内重新核对。真实 SQLite 写锁下验证正确买家、错误买家和关闭强制绑定，覆盖创建参数两种值：[修复前失败及修复后 53 项通过](../../../eval/verification/2026-10-14-r1-owner-read/)。
- 矩阵脚本在清理失败运行之前保存当前档位，达到停止条件后停止本配置；切配置时重建进程。新增 SQLite 锁异常及 Redis 池异常的原始日志出现次数，与初始化重试分开记录。运行镜像 ID 和这两处修复的源码内容指纹写入清单。
- 压测客户端按整轮 180 秒截止，包含排队心跳、停滞读流及重连；强制停止时先保留失败行再继续抛出中断，Locust 仍写 CSV。此前仅按 socket 读超时计时，强制停止可能漏计样本；[修复前失败和修复后 13 项通过](../../../eval/verification/2026-10-14-r1-load-deadline/)包含实际 Locust 截止、停滞与强停 CSV。
- 两处运行时修复后，[完整后端回归](../../../eval/verification/2026-10-14-r1-runtime-fix/pytest.log) 1,998 项通过；镜像构建成功。同口径矩阵复测使用独立证据目录，实测结果随后补齐。

日志中的计数覆盖 Python 显式重试，SQLite 内部 busy timeout 等待次数未知。结果会结合时延、CPU、队列和进程 RSS 解释；0 次显式重试只表示这些分支未触发。

## 本轮停止与容量限制

本轮保留 17 个完整配置，最后 `queue-a4-w4` 完成 4、8 用户档，共 80 档、5,102 次观测运行；`matrix_complete=false`。当前 8 用户档的在途任务、CSV、失败、日志与资源采样完整收尾后，下一档的输出目录检查按用户停止边界触发退出码 1，16 用户档未启动。原始错误输出保留。主进程、Locust 与监控已退出，只停止本实验项目，8080 原预览继续运行。

Docker 4 CPU、共享 SQLite、45 秒加压窗口、每 worker 并发 2、假模型及 3,700 件旧目录下，单 API 进程内 64 用户档错误率 11.85%、完成 P95 39.117 秒，日志出现 SQLite 写锁冲突。单 API／单 worker 入队的 4→8 用户吞吐 0.157→0.159 次/秒，完成 P95 23.482→47.580 秒。1,410 条原始错误含客户端停载和服务失败，保持逐条记录与原统计口径；短窗口观察的锁失败和排队长尾说明当前容量限制，完整性能收益与 CPU 因果继续后续验证。
