# C2 AG-UI 运行入队

## 需求与实现

AGUI_QUEUE_ENABLED 默认 0，同时启用 QUEUE_ENABLED 并配置 REDIS_URL 后，网页运行复用 Redis Streams、消息与会话租约。请求本轮输入参与指纹去重，worker 调用现有 AGUIRuntime.start 并等待终态。运行日志已保存同一 runId 时直接恢复，重投只等待原运行结束。

AGUI_QUEUE_MAX_PENDING 默认 200。队列总待处理量检查与写入在同一 Lua 操作内完成，满载返回 503 和 Retry-After。入队异常回到进程内执行，保存 runtime.degraded 事件。共享模型限流仍保持 Redis 故障时拒绝调用的原语义。

SSE 等待 worker 建立运行日志，仍使用原游标续传；排队状态可查询。取消通过持久日志传递。前端刷新时恢复尚在排队的运行，保留本机记录的待恢复运行号，使用 GET 重新订阅。

关键源码：app/application/agent_runtime.py、app/presentation/ag_ui.py、app/worker.py、app/domain/queue/ports/task_queue.py、app/infrastructure/queue/redis_stream_queue.py、frontend/src/lib/commerceClient.ts。

## 启用与回滚

环境示例见 .env.example，整合部署见 docker/docker-compose.scale.yaml。关闭 AGUI_QUEUE_ENABLED 恢复 API 内执行；已有 worker 应先处理完待执行任务。Redis、SQLite 与原入口保持兼容。代码在 feat/backend-frontend-runtime，与其他功能统一提交 PR。

## 排队等待超时的恢复修复

复核 b1d6f8f 时发现：API 等待 worker 建立日志超时，会输出 RUN_ERROR；队列任务依然存在，前端却按运行终态清除恢复号。已将该响应改为独立的 transport-error 连接信号。传输层结束订阅，保留原运行 ID，用户恢复时只 GET 事件。已恢复连接再次等待超时也保留该行为。

[失败复现](../../../eval/verification/2026-10-14-queue-wait-regression/before.log)确认原响应；[后端复测](../../../eval/verification/2026-10-14-queue-wait-fixed/backend.log)27 项通过。[前端整套与构建](../../../eval/verification/2026-10-14-queue-wait-final/)249 项通过，构建成功；[恢复连接专项](../../../eval/verification/2026-10-14-queue-wait-resume/)25 项通过。首次尝试用流异常传递消息触发未处理拒绝，失败日志保留于 queue-wait-fixed，最终使用正常关闭订阅的方案。
