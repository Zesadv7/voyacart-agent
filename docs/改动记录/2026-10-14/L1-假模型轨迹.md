# L1 假模型轨迹

2026-10-14。按用户后端优先、统一 PR 的指令，在既有部署假模型上补齐压测长度、延迟及确认轨迹。分支 `feat/L1-mock-trajectories` 从统一交付分支 `d71cab7` 创建。

## 实现

- `scripts/loadtest/mock_llm.py` 默认首 token 800 毫秒，之后每个 token 间隔 30 毫秒，回答 300 个模拟 token。每个 Unicode 字符作为一个模拟 token，协议 usage 记录相同口径。
- 默认 10% 的检索选择确认准备分支。选择保存在工具调用 ID 中，后续请求识别原分支；假服务自身无需保存会话。工具只调用现有 `create_order_tool`，后端从已保存的检索证据中选定默认规格，返回待用户批准的确认卡。
- `MOCK_ORDER_RATE` 可固定为 0／1，`MOCK_RESPONSE_TOKENS` 可调回复长度；原首 token／间隔／429 注入配置保留。Compose mock profile 传递参数，业务服务配置保持原样。

## 验证

- [官方 SDK 专项](../../../eval/verification/2026-10-14-l1-final/pytest.log)：13 项通过，覆盖流式工具参数、文本、usage、300 字符与等待序列、0／1 确认分支、默认 0.1 的边界、429，以及原部署合同。
- [部署轨迹](../../../eval/verification/2026-10-14-l1-final/report.json)：真实 Nginx／双 API／双 worker 返回 3 件商品，一次检索、一次确认准备，最终 1 张待批准确认卡、0 个订单。测试显式把分支率设为 1、延迟设为 0.02／0.001 秒，用于链路验收；容量未知。
- 首次诊断脚本错误读取运行快照中的 `orders` 字段，原失败保留在 `l1-trajectories/run.log`；修正后读取权威订单 API，证据在 `l1-trajectories-fixed/`。
- 页面首轮发现精简商品视图缺少 `default_sku_id`，假模型旧取值发生 500。原服务及 worker 日志保留在 `l1-trajectories/`。使用现有单商品订单入口修复，回归覆盖只有 `product_id` 的商品视图。
- 页面复测完成检索、300 字符回复与确认卡显示，确认卡处于待用户批准状态；[截图](../../../eval/verification/2026-10-14-l1-final/application-confirmation.jpg)。实际规格由后端检索证据确定。测试没有批准确认卡。
- [默认延迟实测](../../../eval/verification/2026-10-14-l1-final/timing.json)：无外网的独立容器内，官方客户端收到 300 个模拟 token，首个内容帧 0.988 秒、最后一帧 11.170 秒，包含本机容器与客户端开销；服务睡眠参数仍为 0.8／0.03 秒。该检查单请求运行，未衡量并发容量。

## 使用与边界

启动命令及配置见 README。假模型通过显式 mock profile 启动；退出该 profile 并恢复真实模型地址即可回到真实模型。检索质量、真实 token 计数、真实模型响应、L2 饱和基线与 R1 容量矩阵均不由此结果证明。
