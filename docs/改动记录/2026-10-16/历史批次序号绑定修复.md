## 根因：明确历史序号未绑定

原 `h1-hold-first/candidate/0` 问“第一批第二件的 product_id”。实际请求完整保留第一批顺序 `P28221,P28222,P28223`，后续批次交换为 `P28221,P28223,P28222`。候选布局没有调用历史回查，错误回答 `P28223`；当前布局调用 `conversation_fact_lookup(batch=1,position=2,fields=identity)` 并正确回答 `P28222`。

这证明本例存在跨批次位置指代错误，不能归因为商品漏召回或目录错序，也不足以证明某种 Prompt 布局必然导致该错误。

## 最小修复边界

1. 仅识别最新真实买家原文中单一、明确的历史批次及商品序号，而且问题仅请求身份信息。不绑定评测 ID、具体商品或整句模板。
2. 复用现有会话证据存储和只读回查工具；在当前 reply 的独立作用域中绑定批次/位置，缺省参数可补齐，显式矛盾参数拒绝，不能静默改查最新批次。
3. 仅首次取证强制已有只读工具，附加结构化选择说明；工具响应后解除强制，错误不触发无限循环。
4. 多批比较、否定、歧义、当前价格/库存及交易混合请求不猜测；审批、工具禁用、买家/会话隔离、取消清理及普通回查原语义必须保留。

底层商品排序、压缩算法、模型参数、原 fixture 和原评分不变。完整业务和 Harness 共用上下文中间件，不添加评测专用答案路径。

具体落点为 `visible_evidence.py` 的保守序数识别与请求选择、`context_governance.py` 的 reply-local 作用域、`conversation_fact_lookup.py` 的取证参数校验；工具函数签名和 docstring 与基线相同。另在 `llm.py`、`model_protocol.py` 将此强制只读取证纳入已有完整响应及缺工具失败关闭边界。强制取证的合法工具响应若夹带正文，仅对响应副本清空未经取证的可见正文，保留工具、推理字段、模型身份与用量；后续正常续答以及普通 auto/none 不改变。

独立审查曾发现并修复两项边界：合法 lookup 夹带错误抢答可提前外流，以及大标题的 identity 分片续查被过度限制。现同批、同件的 `field_offset` 续查和普通 query 不筛选已指定批次的原语义均保留，矛盾商品或非零商品页偏移明确报错。

## SKU 题意的独立版本规范

原 `h1-hold-black/current/0` 和 `candidate/0` 均给出三个目标黑色 SKU，但同时列出对应商品的其他颜色 SKU，未通过原评分的全文 SKU 集合相等要求。原问题“哪些商品有黑色规格？给出全部 SKU”允许“这些商品的全部规格”这一理解。原失败保留，不回写通过。

后续诊断规范单独标识为 `historical-sku-scope-v2`，尚未作为可运行 suite 发布：

- `black-only`：问题明确为“请只列出第一批商品中颜色为黑色（含曜石黑）的全部 sku_id，其他颜色的 SKU 不要列出。”期望集合由该批全部商品中规格名称含“黑”的 SKU 推导，要求完整、无额外 SKU。
- `all-skus-of-black-products`：问题明确为“请找出第一批中至少含一个黑色（含曜石黑）规格的商品，再列出这些商品的所有 sku_id，包括非黑色规格。”期望集合先筛选含黑色规格的商品，再取其所有 SKU，要求完整、无额外商品的 SKU。
- 两项必须有不同案例 ID、题目/数据指纹及独立结果，不能混进旧 v1.1 的分数。已检查过的原留出场景今后只能作为已见回归样本，不能再宣称是未见留出数据。
